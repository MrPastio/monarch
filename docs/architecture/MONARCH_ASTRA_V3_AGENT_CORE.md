## 1. Цель

Astra V3 должна быть не новым набором схем поверх V2, а новым способом выполнять
задачи:

1. Правильно понять, требует ли запрос ответа, наблюдения или реального эффекта.
2. Превратить запрос в типизированные требования и исполнимый граф, а не повторно
   интерпретировать prose в каждой подсистеме.
3. Выбирать минимальный путь: deterministic fast path, готовый workflow или модельное
   решение — именно в таком порядке.
4. Давать локальной модели малый, релевантный и schema-constrained decision surface.
5. Выполнять capability только через Kernel и никогда не считать model text фактом.
6. Продолжать, приостанавливать и восстанавливать задачу после сбоя модели, процесса
   или UI без повторения уже выполненного эффекта.
7. Завершать задачу только тогда, когда доказаны конкретные требования пользователя.
8. Измеримо уменьшить число model calls, объём контекста, cold-loads и время до
   первого полезного действия.
9. Поддержать реальные многошаговые agent workflows, steering, cancel/resume,
   bounded children и background jobs без скрытого расширения полномочий.

| P06 | нужная capability выпадает из resolver window | Capability Catalog |
| P07 | runtime отсутствует уже после user admission | Runtime Readiness + Product Facade |

| P10 | zombie `running` / `waiting-for-runtime` | Scheduler + Recovery Supervisor |
| P11 | context overflow решается обрезанием или отказом | Context Engine + Compaction |
| P12 | Agent-First может вернуться через routing drift | one Admission artifact |
| P13 | God-loop владеет routing, workflow, recovery и truth | разделённые domain services |
| P14 | модельное планирование обязательно даже для простого действия | Strategy Selector |

Нужен соответствующий end-to-end acceptance scenario на обычном route.

## 4. Product closure: `astra-core-experience.v1`

### 4.1. Обязательные foundation-профили

`astra-core-experience.v1` является release composition, а не новым wire protocol.
Он обязан включать одновременно:

1. `agent-product-facade.v1` — один ingress, continuation, query, cancel, delivery.
2. `agent-admission.v1` — PreliminaryNeeds discovery и единый final typed admission.
3. `agent-goal.v1` — capability-owned Requirement/Claim compilation.
4. `agent-strategy.v1` — deterministic/workflow/model selection and call ceilings.
5. `agent-engine.v1` — transport-only driver + Decision Gateway, resume/cancel.
6. `agent-catalog.v1` — required pinning, search, inspect, revision/digest.
7. `agent-context.v1` — ContextPlan, acknowledged deltas and redaction.
8. `agent-compaction.v1` — coherent model view with raw authority/evidence retention.
9. `agent-model-host.v1` — resource leases, residency, one GPU queue owner.
10. `agent-scheduler.v1` — readiness receipts, activation lease, deadlines, recovery.
11. `agent-steering.v1` — durable follow-up, cancel acknowledgement, safe resume.
12. `agent-workflow.v1` — durable typed task graph and first-party workflows.
13. `agent-completion.v1` — evidence projection, assessment, certificate,
   presentation.
14. `agent-core-read.v1` — deterministic read substrate.

`agent-memory.v1` пока не включается как доступная product-функция, но его
`MemoryAuthority`/consent/byte-budget foundation является обязательным условием
архитектуры: Context и Compaction нельзя реализовывать так, чтобы затем понадобился
второй store или несовместимая миграция ради глобальной и межчатовой памяти.

Если любой из пунктов 1–13 unavailable, лабораторный read slice может продолжать
развиваться, но продукт не называется Astra V3 и не идёт в default cohort.

### 4.2. Обязательные capability packs для первого product cohort

Первый cohort обязан доказать не один демонстрационный tool, а минимум пять разных
классов поведения:

- `workspace-read`: root/list/search/storage audit с typed factual claims;
- `workspace-effects`: create/write/append/move/trash с exact target и readback;
- `desktop-control`: app open и bounded state read/set;
- `browser-navigation`: open named browser → navigate exact URL → observe target;
- `computer-use-reliability`: multi-step UI через exact observation → one atom →
  fresh observation → evidence verification, а не отдельный regex fast-path.

`download` не подменяется search. Если `network-download` pack не включён, запрос
завершается typed `capability-unavailable`, а не false `verified`.

### 4.3. Обязательный `astra-computer-use.v1`

Нативный V2-контур сохраняет полезные примитивы — exact window, one-shot observation,
input lease, emergency Stop и readback. Но его orchestration не переносится в Astra:
обычная задача зависит от leading `@Computer Use`, `computer-use-goal.ts` и
`computer-use-workflow.ts` компилируют узкий RU/EN regex, а planning/retry/completion
находятся в `agent-loop.ts`. Поэтому source-green single-window acceptance не означает
работоспособность общей агентской функции.

`config/agent-architecture/astra-v3-computer-use-reliability-pack.v1.json` задаёт
отдельный mandatory profile. Его минимальный цикл неизменяем:

```text
admit semantic UI requirement
  -> resolve exact top-level window
  -> observe window + UIA + screenshot + focus/modal/geometry/topology identity
  -> decide exactly one semantic atom
  -> consume observation and reserve exact Kernel input
  -> native pre-dispatch recheck
  -> dispatch
  -> fresh observe
  -> verify postcondition or enter typed recovery
```

Координаты модели никогда не являются authority. Target — opaque server-owned handle
из exact observation; UIA/vision ambiguity ведёт к clarify/reobserve. Observation
связывает control epoch, process/HWND generation, foreground/focus, modal chain,
physical client rectangle, monitor origin, rational DPI scale, display topology,
UIA/screenshot digests и capture sequence. Любое расхождение до native input
инвалидирует reservation.

Crash после non-idempotent dispatch без receipt создаёт `RecoveryCaseV1` и
`indeterminate`; повторять click/type/key вслепую запрещено. Stop/takeover вращает
control epoch до завершения процесса и fences buffered model decisions. Secure
desktop, credential/password target и Production Monarch Safe не получают input.
Completion требует dispatch receipt, fresh same-window observation и точный
postcondition; cursor animation, native exit code и model prose доказательством не
являются.

### 4.4. Advanced profiles

Children, jobs, providers, plugins и encrypted execution могут
включаться отдельными profiles. Но архитектура ядра обязана иметь их bounded seams;
иначе следующая функция снова разрастит `AgentLoop`.

## 5. Целевая runtime-топология

```text
Surface adapters
  -> Product Facade
     -> Preliminary Needs (authority=none) -> bounded Catalog discovery
     -> Final Intent Admission
        -> answer-only ---------------------------------> Answer Runtime
        -> clarify -------------------------------------> Interaction
        -> operational
           -> Goal Compiler -> Requirement Set
           -> Strategy Selector
              -> deterministic recipe
              -> registered Workflow Graph
              -> bounded Model Planner
           -> Task Graph Store
           -> Scheduler / Recovery Supervisor
              -> Capability Catalog (search + inspect)
              -> Context Engine (ContextPlan + delta snapshot)
              -> Decision Gateway
                 -> Engine Driver / Local Model Host
              -> Workflow Runtime
                 -> Kernel Invocation / Approval / Receipt
              -> Evidence Projector
              -> Completion Certifier
           -> Outcome Projector -> durable message/UI
```

### 5.1. Dependency rule

- Product Facade знает application commands, но не tool-specific regex.
- Admission знает intent grammar, но не исполняет capability.
- Goal Compiler использует capability-owned compiler contracts.
- Strategy Selector выбирает класс исполнения, но не выдаёт authority.
- Model Driver возвращает proposal, не Task state и не verified outcome.
- Workflow Runtime меняет workflow state только через persisted transition.
- Kernel остаётся единственным владельцем факта попытки/эффекта.
- Certifier читает frozen Goal + admitted evidence и является pure service.
- Presentation не может усиливать certificate.

## 6. Один Intent Admission вместо нескольких semantic parser

### 6.1. Артефакт

`InteractionIntentAdmissionV1` содержит:

- normalized user clauses и их original spans;
- `authority = none | observe | effect`;
- `lane = answer | execution | clarify | memory`;
- типизированные target candidates;
- required capability classes;
- ambiguity records;
- privacy/egress/attachment modifiers;
- admission revision/digest.

Disposition, Goal Compiler, required-capability pinning и UX читают один artifact.
Они не запускают собственные regex-интерпретации исходного текста.

### 6.2. Морфология и смешанные запросы

Русские падежи, app aliases, paths, URLs и known folders обрабатываются bounded
lexicon/normalizer слоями с golden corpus. Смешанный запрос разбивается на clauses:
answer, observe и effect могут сосуществовать в одном Interaction, но каждый effect
получает отдельное Requirement и authority scope.

### 6.3. Fail behavior

- greeting и обычный вопрос никогда не создают Execution;
- current local fact не уходит в ungrounded answer;
- imperative без точной цели становится `clarify`, а не guessed effect;
- неизвестная capability-class становится `capability-unavailable` или catalog
  discovery, а не model-invented ID.

### 6.4. Двухфазное admission для открытой задачи

Открытая, но потенциально выполнимая задача не блокируется до того, как runtime
получил возможность найти подходящие capability. До authority-bearing admission
существует отдельный `PreliminaryNeedsV1`:

- clauses, target hints, desired outcome classes и ambiguities;
- `authority = none` и запрет создавать Execution/Invocation;
- digest исходного user turn и catalog revision used for discovery;
- bounded discovery budget и список допустимых semantic capability classes.

Catalog discovery получает только этот artifact и возвращает bounded candidates.
Модель может ранжировать или предложить composition **только из exact returned
handles**; она не создаёт capability ID, target, scope, input или permission. Затем
детерминированный compiler формирует `InteractionIntentAdmissionV1`, Goal и
Requirements. Финализация монотонна: authority, target и capability могут только
соответствовать user clauses/policy и выбранному catalog snapshot; любое расширение
возвращает `clarify` или `capability-unavailable`. Preliminary artifact не является
разрешением и не переживает catalog/policy revision без повторного discovery.

## 7. Goal Compiler и Task Graph

### 7.1. Requirement, а не prose acceptance

Каждый обязательный результат имеет:

- stable requirement ID;
- capability contract/version;
- typed inputs и target identity;
- effect class;
- required claims/selectors;
- verification strength;
- temporal semantics;
- dependency IDs;
- failure/substitution policy.

Original prose сохраняется для аудита и clarification, но не является единственным
источником execution truth.

### 7.2. Task Graph

Task Graph хранит runtime-owned nodes:

- `observe`, `effect`, `verify`, `synthesize`, `clarify`, `reduce`;
- dependency edges;
- retry/idempotency class;
- required capability ID/class;
- workflow state ref;
- budget slice;
- terminal contribution.

Модель предлагает graph patch только в разрешённой области. Runtime выдаёт IDs,
проверяет acyclic dependencies и связывает nodes с Requirements. Для известного
workflow graph строится детерминированно без planning model call.

### 7.3. No substitution

`search` не выполняет `download`; `open browser` не выполняет `navigate URL`;
workspace root не доказывает Desktop file; process started не доказывает UI target.
Замена возможна только как отдельная user-approved Goal revision.

## 8. Strategy Selector: меньше модели, больше агента

Порядок выбора стратегии обязателен:

1. **Answer fast path** — no execution authority, no AgentTask.
2. **Deterministic recipe** — exact request полностью компилируется capability
   contract; zero planning calls.
3. **Registered workflow** — известная многошаговая state machine; model call только
   для действительно семантического выбора.
4. **Bounded model planning** — неизвестная или открытая задача; proposal проходит
   Task Graph validator.

Нельзя отправлять каждое `открой калькулятор` в planning → execution → completion
три model-turn цикла. Минимальная цель первого cohort:

- simple exact read/effect: 0 planning calls, не более 1 optional synthesis call;
- registered workflow: 0–1 planning calls;
- open-ended multi-step: bounded calls по progress, а не по каждому persisted event.

### 8.1. `MAX`: простой облачный режим Astra V3

`MAX` является отдельным пользовательским режимом Astra V3, а не другим runtime и
не переключателем между V2/V3. Он нужен для сложных задач и для устройств, которым
не хватает локальной производительности. Первый bounded catalog содержит только:

- `openai/gpt-oss-120b` — основной text/reasoning/tool provider;
- `qwen/qwen3.8-27b` — text/reasoning/tool/vision provider;
- `openai/gpt-oss-safeguard-20b` — отдельный policy classification stage, не
  обычная разговорная модель.

Внутренне `MAX` использует `agent-provider.v1` + Decision Gateway и не получает
Kernel authority. Provider возвращает только proposal; tools, Computer Use,
workspace effects, approval, readback и Completion остаются у Monarch. Provider
grant связывает exact provider/model/capabilities, consent revision, разрешённые
классы данных, срок и Execution; ребёнок, plugin или другой chat не наследует его.

Первое включение обязательно показывает короткое человеческое предупреждение по
образцу облачной генерации изображений: обработка не локальная, какие данные могут
быть отправлены, зачем это требуется и как отключить режим. До принятия актуальной
версии consent сетевой запрос запрещён. API key вводится пошагово, проверяется без
показа значения и хранится только через защищённый main-process secret boundary;
renderer, URL, localStorage, telemetry, prompt, log и evidence не получают ключ.

Capability negotiation выполняется на каждую выбранную модель: различия reasoning,
tool calling, vision, structured output, context, rate limit и preview/production
status нельзя скрывать за общим предположением совместимости. Network timeout,
cancel, quota и uncertain response не разрешают повторный non-idempotent Kernel
effect. Недоступность `MAX` возвращает понятный выбор: повторить позже или продолжить
локально до создания нового Execution; mid-task подмена truth owner запрещена.

Статус: **source-only product pilot / недоступно обычному пользователю**. Изолированный
`AstraGroqMaxProvider` уже закрепляет точный endpoint и allowlist, актуальный
versioned consent до доступа к ключу/сети, pre/post safety, строгий JSON proposal,
отсутствие provider tools и `authority: none`. Ответ, остановленный лимитом, и
невалидная схема отклоняются; ошибки провайдера и хранилища ключа не раскрывают их
тела. Host-only `AstraMaxSettingsStore` сохраняет ключ и consent одной OS-protected
записью, не имеет renderer-сериализации, требует отдельный ACL policy и не заменяет
повреждённую запись молча. Изолированный `decideAstraReadWithMax` уже пропускает proposal через тот же
Read Decision Gateway: модель выбирает только заранее посчитанные opaque handles,
а точный путь и лимиты заново подставляются из host-owned candidate. Мост не принимает
Kernel/tool/effect port. Отдельный exact-version loader уже прошёл
изолированный Windows Electron acceptance с реальным `safeStorage` и ACL: защищённая
запись сохраняется и открывается после нового loader instance, открытого ключа в ней
нет. Реализован setup-only интерфейс первого включения: он объясняет нелокальную
обработку, собирает актуальный consent и ключ, но renderer не получает ключ,
provider payload или метод запуска модели. Main-process host теперь поднимает
authenticated loopback prepared-model bridge только при одновременных source
switches Astra pilot + MAX preview и подключает его к существующему
`AstraPreparedModelClient`, Oscar/Application и Kernel, не создавая второго owner.
Сквозной тест доказал proposal -> exact approval -> единственный Kernel create и
одновременно нашёл реальный обход: permissive Kernel profile позволял model draft
писать до подтверждения. Теперь composite model draft и literal create через facade
всегда требуют exact confirmation; до него файл отсутствует.

Первый полный source Electron запуск с обоими pilot switches выявил ещё одну
практическую проблему: Astra скрывала MAX вместе со всеми legacy model controls.
Теперь только явно допущенный MAX setup переносится в Astra-owned composer, а
остальные legacy элементы остаются скрыты и disabled. Реальный main/preload/runtime/
renderer проход сохранил ordinary exact read, показал только credential-free
`status`/`configure`, не вызвал модель или внешнюю сеть и завершился без оставшегося
Electron-процесса.

Следующий полный UI model-draft проход обнаружил разрыв уже между внутренним
decision ABI и облачным transport: Astra использует корневой `oneOf`, а Groq strict
structured output требует object root и документирует `anyOf`. Provider теперь
формирует закрытую wire-обёртку `{proposal: anyOf(...)}`, заменяет `const` на
одноэлементный `enum`, отдельно проверяет wire-ответ, снимает обёртку и повторно
проверяет исходный неизменённый `oneOf`. Поэтому даже возможное расширение семантики
`anyOf` не даёт proposal пройти дальше. Реальный source Electron UI с синтетическим
ключом прошёл setup -> Safety -> GPT OSS 120B -> Safety -> exact approval -> один
Kernel create; до подтверждения файла не было, после него exact readback совпал.
Внешняя сеть, Safe и пользовательские данные не использовались. Это первая полная
детерминированная модельная задача в product pilot, но всё ещё не real-Groq
acceptance и не доступный пользователю режим.

Выбор двух основных моделей теперь также имеет отдельный host-owned policy.
`automatic` закреплён за production GPT OSS 120B; Qwen 3.8 27B допускается только
явно и после отдельного подтверждения его Preview-статуса. Произвольный provider ID,
требование облачных tools, image input при текущем text-only ABI и output сверх
8,192 токенов блокируются. Qwen получает собственный model digest, поэтому его
нельзя незаметно подменить внутри уже открытого Execution. Exact-version loader
прошёл синтетический Qwen-путь Safety -> Qwen -> Safety без сети. В UI этот выбор
пока не выведен, автоматический product pilot по-прежнему использует GPT OSS.

Отдельный source-only Qwen gate теперь также проходит весь реальный product путь.
Electron main принимает только точный dev-флаг, игнорирует его без MAX preview,
повторно проверяет bounded preference и закрепляет Qwen до запуска prepared host и
runtime child. Renderer не видит model ID, preview grant, endpoint или digest. UI
задача проходит Safety -> Qwen -> Safety -> exact approval -> Kernel create без
файла до подтверждения и с точным readback после него. Это доказывает обе primary
модели в source pilot, но не является горячим переключением, пользовательским меню
или real-Groq acceptance.

Это всё ещё не обычный пользовательский режим: product pilot пока запускает
automatic/GPT OSS 120B, Qwen не выведен в UI, нет default routing,
точного MAX tokenizer/compaction и реального Groq/model acceptance. MAX намеренно
удалён из требований installer/runtime bundle/offline payload: на текущем этапе
установщик не нужен и не создавался. Сеть в текущем тестовом срезе замещена
детерминированным fetch.

На 2026-09-04 официальные страницы Groq указывают окно 131,072 токена для
GPT OSS 120B и 131,042 для Qwen 3.8 27B; Qwen при этом имеет статус Preview.
Публичный Chat Completions API не даёт найденного нами отдельного preflight
tokenization contract. Поэтому ранний adapter не переиспользует локальный token
count как якобы точный: до model-specific tokenizer gate он принимает не более
80 KiB текста, 24 KiB schema и 16,384 output/reasoning tokens, оставляя защитный
запас под framing в меньшем окне. Это сознательная временная потеря ёмкости, а не
финальная стратегия больших контекстов. Источники:
`https://console.groq.com/docs/model/openai/gpt-oss-120b`,
`https://console.groq.com/docs/model/qwen/qwen3.8-27b`,
`https://console.groq.com/docs/api-reference`.

## 9. Decision Gateway: permissive syntax, strict semantics

### 9.1. Три стадии

1. **Constrained generation**: driver получает branch-specific discriminated schema,
   а не общий объект со всеми optional fields.
2. **Syntax canonicalization**: code fence, benign wrapper, inert unknown metadata,
   omitted empty arrays и known alias формы нормализуются по versioned rules.
3. **Semantic admission**: capability ID, input schema, Goal binding, secrets,
   untrusted provenance, policy и authority проверяются строго.

### 9.2. Что можно исправлять без нового model call

- убрать schemaVersion после проверки;
- извлечь единственный JSON object из разрешённого wrapper;
- отбросить только поля из versioned branch-local inert allowlist;
- добавить runtime-owned empty arrays/defaults;
- canonicalize известный non-executable plan wrapper;
- заменить capability-keyed envelope на exact branch, если capability уже pinned.

### 9.3. Что нельзя исправлять

- неизвестный capability ID;
- secret-bearing или credential-like data;
- новое target/value;
- input, скопированный из untrusted observation без разрешённого handle binding;
- расширение scope/authority;
- claim/evidence IDs, которых нет в текущем snapshot;
- двусмысленную смесь двух executable decisions.

`capabilityId`, `input`, `arguments`, `target`, `approval`, `authorization`,
`evidence`, `artifactIds`, `claimIds` и любой effect/authority handle являются
authority-bearing независимо от выбранного `kind`. Они никогда не отбрасываются как
metadata: поле другой branch делает candidate semantic-invalid. Для `respond`
первый allowlist содержит только `schemaVersion` и явно versioned audit correlation;
неизвестное поле отклоняется, пока его inertness не доказана в protocol version.

Repair model call разрешён только после deterministic rejection и получает compact
error code + allowed branch schema + refs, но не полный invalid payload.

## 10. Capability Catalog и Workflow Runtime

### 10.1. Catalog

Catalog предоставляет summary search и schema inspect. Requirement-required
capability закрепляется вне relevance window. Candidate limit применяется только к
optional discovery, поэтому нужный tool не может исчезнуть из-за top-N.

Driver получает:

- короткие capability handles;
- schema только inspect-selected candidates;
- revision/digest;
- readiness/cancellation/approval flags;
- reason отсутствия required capability.

### 10.2. Workflow as data

Workflow определяет state, transitions, allowed capability, observation selector,
retry policy и completion contribution. Первые обязательные workflows:

- app search → exact app open → process/window readback;
- named browser open → exact URL navigate → address/title observation;
- file preflight → effect → exact readback;
- recoverable move/trash with reconciliation;
- storage audit → typed field projection;
- Computer Use observe → one atom → fresh observe.

Workflow-specific code может жить рядом с capability pack, но core scheduler не
содержит `trusted*` branches для каждого приложения.

### 10.3. Исполняемый ownership/deletion и strategy contract

P13/A22 больше не ограничен пожеланием «разнести `agent-loop.ts`». Exact-source inventory
закрепляет все `36` объявленных там `trusted*/isTrusted*` helpers и требует ровно одного owner:
Capability Catalog `1`, Goal Admission `1`, Recovery Supervisor `3`, application workflow `3`,

`SourceDiffManifestV1` для каждой migration family связывает legacy path/function/declaration
digest с новым owner и replacement contract. Deletion gate проверяет projected core: разрешены

application/workspace/browser/calculator/Computer Use literals запрещены. Workflow definition

## 11. Context Engine и Compaction

### 11.1. ContextPlan

Перед сериализацией создаётся explicit `ContextPlan`:

- mandatory Goal/Requirement slice;
- active Task Graph nodes;
- current workflow state;
- latest relevant evidence refs;
- inspected capability schemas;
- authority/privacy/budget facts;
- omitted ranges и reason;
- token estimate per driver tokenizer;
- snapshot digest.

Context выбирается по causal relevance, не просто `slice(-N)`.

### 11.2. Delta snapshots

Driver session может объявить prefix/session cache, но delta запрещена до handshake
`DriverContextSessionV1`:

```text
no-session -> base-offered -> base-acked -> delta-allowed
                                |                |
                                +---- stale <----+
                                         |
                                         +-> full-rehydrate -> base-acked
```

Base acknowledgement связывает `baseDigest`, driver generation, model/build/config
digest, tokenizer, catalog revision и mandatory authority/Goal minimum. Каждая delta
имеет monotonic sequence, previous digest, resulting digest и exact added refs.
Missing/out-of-order delta, cache eviction, Host/driver restart, model/config change,
unknown acknowledgement или stale catalog/policy переводит session в `stale`; Host
обязан сделать full rehydration и получить новый ack до следующего decision.

После ack Host передаёт signed/digest-bound delta: new observation, steering, policy
change, graph transition. Полный replay всегда доступен для recovery. Драйвер не
может заявить decision, если receipt не подтверждает, что mandatory Goal, authority,
active nodes и evidence frontier относятся к exact accepted base/delta digest.

### 11.3. Compaction

Compaction суммирует только optional narrative/history. Goal, authority, approvals,
invocations, receipts, required evidence и active workflow state не заменяются
summary. Crash между start/complete оставляет старую projection authoritative.

Автосжатие обязательно и принадлежит `ContextBudgetAccountant`, а не модели. Он считает
полный model-visible surface точным tokenizer-ом выбранного driver-а. При soft pressure
создаётся bounded background single-flight bracket до следующего turn; на hard boundary
перед submit выполняется synchronous bracket. Если он не прошёл CAS/source binding,
не вернул минимум экономии или не уложился в hard budget, driver не вызывается и Runtime
возвращает typed `context-capacity-insufficient`/`compaction-failed`; silent truncation
запрещён. Hysteresis повторно разрешает trigger только после снижения ниже rearm watermark,
а на одну surface revision допускается одна попытка.

Foundation compactor детерминированно заменяет только старый optional range одним
digest-bound `compaction-summary`, оставляя bounded recent tail raw. Summary всегда
`authorityEligible=false`; source range/digest, before/after units, omitted refs и bracket
state входят в receipt. Raw journal не удаляется. Model-generated summary в foundation
выключен: более умное semantic summary может появиться отдельным profile, но остаётся
untrusted и не ослабляет тот же hard gate.

### 11.4. Memory

Память — отдельный владелец `MemoryAuthority`, а не массив сообщений внутри Engine.
Он использует тот же authority database/migration contour, что действующая Memory V4;
параллельный Astra-store запрещён. В Context попадает только
`MemoryContextReceiptV1`, связанный с exact `ContextPlanV1`. Память никогда не владеет
Goal, policy, capability authority или Completion truth.

Нормативный foundation закреплён в
`config/agent-architecture/astra-v3-memory-foundation.v1.json`. Это design contract,
не реализация retrieval и не разрешение миграции production SQLite.

### 11.5. Уровни и границы памяти

1. `active-turn` — ephemeral Execution journal/projection; не long-term memory.
2. `conversation-checkpoint` — derived/rebuildable summary exact conversation refs.
3. `cross-chat-episode` — revocable derived memory, выключена без versioned consent.
4. `explicit-durable` — typed `remember` command либо принятый пользователем preview.
5. `user-global` — только явно подтверждённый пользователем факт/предпочтение.
6. `project-module` — exact project scope; cross-project retrieval запрещён.
7. `capsule-index` — rebuildable cache, а не источник истины.

Автоматическое продвижение `turn -> conversation -> project -> global` запрещено.
Child/workflow/model summary не становится durable user fact. Новая explicit correction
помечает старый факт `superseded` и инвалидирует зависимые summaries/indexes; физическое
перезаписывание не подменяет lineage.

`Incognito`, encrypted conversation и Monarch Safe не создают обычную durable memory.
Safe запрещён также для discovery, FTS, embeddings, WAL fixtures и backup corpus.
Voice, Telegram и API остаются excluded до собственного source/consent contract.
Legacy `cross_chat_enabled=true` по умолчанию не считается согласием Astra:
межчатовая память использует новый receipt `astra-v3-memory-v1` и default-off.

### 11.6. Сводки, глобальный context и retrieval

`MemorySummaryV1` содержит exact child refs/digest, source revision, отдельные
statements с support refs, известные contradictions, algorithm/model identity и state
`prepared | active | superseded | invalid`. Summary не владеет authority, не скрывает
известное противоречие и активируется CAS только при совпавших scope/consent revisions.
Crash до complete оставляет предыдущую projection authoritative.

Для каждого model turn MemoryAuthority компилирует bounded
`MemoryContextReceiptV1`: query digest, scope/consent revisions, exact UTF-8 byte budget,
selected refs, omitted refs/reasons, retrieval engine и итоговый ContextPlan digest.
Приоритет: current constraints → confirmed global facts → current conversation → exact
project → consented cross-chat episodes → capsules. Все recalled тексты помечаются
untrusted data и не могут менять instructions, Goal, policy или tools.

Retrieval остаётся дешёвым: scope-filtered FTS до 32 candidates, затем optional local
semantic rerank с deadline 120 ms. Timeout возвращает lexical order с provenance;
корректность не зависит от embeddings. Cache key обязан включать scope revision,
consent revision, query и retrieval-policy digest.

### 11.7. Каждый мегабайт учитывается

Бюджеты считаются по exact UTF-8/SQLite pages, не символам и не числу rows. Базовый
profile: soft `32 MiB`, hard `64 MiB`, отдельно не более `16 MiB` transient WAL/migration;
model-visible memory projection — default `3072 B`, hard `4096 B`.

`MemoryByteLedgerV1` считает по каждому scope `liveBytes`, `indexBytes`,
`reclaimableBytes`, `pinnedBytes`, `walBytes`. Один normalized content body адресуется
SHA-256 и переиспользуется typed refs; immutable Interaction bodies не копируются в
episode. Durable `search_text` запрещён, FTS — contentless/external-content и rebuildable.
Persistent semantic index default-off; если отдельный benchmark его оправдает, он
остаётся bounded, local, quantized и evictable.

При soft pressure сначала удаляются cache/optional indexes, затем invalid derived
projections и только потом компактируются eligible derived bodies. Hard limit блокирует
новые derived writes. Explicit/pinned user facts никогда не удаляются молча: система
показывает storage-management preview. GC использует bytes, lineage, consent и refs, а
не `COMPACT_AFTER = N rows`; reclaim разрешён только после tombstone, transitive
invalidation и отсутствия live refs.

### 11.8. Совместимость с Memory V4

Сохраняются её хорошие seams: один SQLite owner, WAL/transactions, scope revisions,
revision-bound cache, FTS-first retrieval, optional bounded rerank и provenance.
Исправляется фундамент: нынешняя row-compaction удаляет episode из FTS, но оставляет
полные `user_text`, `assistant_text`, `summary`, `search_text`, поэтому почти не
освобождает DB bytes.

Миграция только staged: `M0` contracts/ledger без product schema mutation; `M1`
additive content blobs/refs/consent/tombstones в том же DB; `M2` shadow dual-read с
parity/delete/byte tests; `M3` authority cutover и только после backup-restore proof —
reclaim старых duplicated columns. Ни один текущий документ не разрешает M1–M3.

## 12. Resource-aware Model Host

### 12.1. Driver feature negotiation

Driver объявляет:

- context/token limits;
- branch schema / grammar support;
- cancellation and preemption granularity;
- session/prefix cache support;
- multimodal/tool-call support;
- cold-load estimate и current residency;
- memory requirement and health;
- maximum parallel model turns.

Scheduler не предполагает одинаковые возможности Gemma, Qwen и external endpoint.

### 12.2. Один GPU slot — явное ограничение

На 8 GB GPU модельные turns сериализуются. Параллельными могут быть безопасные
read-only I/O и независимые Kernel observations, но не два тяжёлых GGUF inference.
Children не создают иллюзию параллельного LLM; Scheduler применяет fair queue,
deadline и budget.

### 12.3. Нормативный resource protocol

Резидентность модели и владение одним inference turn — разные aggregates.

`ModelResidencyRecordV1`:

```text
absent -> loading -> resident -> evicting -> unloaded
              |          |          |
              +----------+----------+-> failed
```

Record связывает Host generation, driver/model/build/config, RAM/VRAM committed bytes,
backend handles, cache/residency generation и last-used/eviction policy. Он может жить
между turns; `resident` не означает занятый GPU execution slot.

`InferenceTurnLeaseV1`:

```text
requested -> queued -> reserved -> generating -> releasing -> released
      |          |          |            |             |
      +----------+----------+------------+-------------+-> failed | expired
```

Turn lease связывает queue lane, Execution/turn, exact Residency generation,
temporary RAM/VRAM/KV reservation, deadline/start-by, context receipt и cancellation
generation. После generation он всегда освобождается; Residency при этом может
остаться warm. Только Host CAS может менять оба aggregates, но их revisions и
lifetime не смешиваются.

- residency/load reservation сверяется с live RAM/VRAM до load; turn/KV reservation
  повторно проверяется перед `reserved -> generating`;
- warm path ссылается на existing exact Residency generation и не делает фиктивный
  `loading`; cold path сначала доводит Residency до `resident`, затем выдаёт turn;
- load/OOM не меняет Goal: Host освобождает turn, помечает/evict-ит failed Residency и
  Scheduler выбирает объявленный fallback или typed `resource-unavailable`;
- любой fallback на другой model/build/backend/CPU инвалидирует старые inference-turn
  и context bindings, получает новый `InferenceTurnAdmissionReceiptV1`, новую
  Residency/Turn binding и full context rehydration/ack до decision; общий
  model-free Execution receipt остаётся действителен только для deterministic nodes;
- Fast → Balanced является двумя видимыми scheduled turns с отдельными leases и
  telemetry, а не внутренним retry одного driver call;
- cancel во время queue/load/generation запрещает следующий dispatch, освобождает
  turn lease, ждёт exact
  driver acknowledgement либо fence-ит Host generation;
- cache eviction/unload меняют residency generation и инвалидируют context session;
- после Host crash Recovery Supervisor fence-ит старые Residency/Turn generations,
  освобождает orphan turn/KV reservations и не предполагает, что model/handles живы;
- answer, agent, synthesis, child и job turns используют одну fair queue с явными
  lane weights/deadlines; никакой профиль не создаёт второй скрытый GPU owner.

#### 12.3.1. Изолированный ResourceModelHost proof

Нормативный protocol закреплён отдельным architecture-only simulator corpus для P15 и A24/A25.
Он pinned к фактическим V2 source roots: `inference_coordinator.py` (`6525` bytes,
`sha256:fe5af0474089f37975f4712c1f3c1636806794151892d514c9829ffa4a89be62`),

### 12.4. Оптимизации

- deterministic/registered workflow до model call;
- resident-tier affinity и запрет лишнего restart/swap;
- branch-specific малые schemas;
- token-aware ContextPlan и delta;
- Fast только при confidence gate;
- Balanced escalation только один раз на progress generation;
- reuse уже полученного valid decision — без повторного synthesis;
- explicit queue/load/generation telemetry;
- cancellation освобождает lease и запрещает следующий dispatch.

### 12.5. Обязательные SLO, не пожелания

SLO калибруются на поддерживаемом hardware matrix, но release gate обязан фиксировать:

- time-to-admission p50/p95;
- time-to-first-useful-action p50/p95;
- warm/cold decision latency;
- model calls и input tokens per completed task;
- model swap count;

## 13. Scheduler, recovery и partial truth

### 13.1. До создания Execution

Product Facade не полагается на boolean preflight. Перед созданием runnable
Execution Runtime Readiness выдаёт `ExecutionReadinessReceiptV1`, связывающий:

- Product Facade/store/Kernel/Scheduler generations;
- capability ID/version/manifest digest и activation status;
- catalog revision, policy/auth epoch и revocation cursor;
- start-by/deadline/expiry и recoverability mode;
- Goal/admission/strategy digest, required capability set и discriminated
  `modelRequirement = none | immediate | deferred`.

`modelRequirement=none` запрещает driver/model/residency/turn fields и позволяет
deterministic recipe/known workflow работать при полностью недоступной модели.
`immediate` требует отдельный `InferenceTurnAdmissionReceiptV1` непосредственно перед
model turn; он связывает Host/driver/model/build, exact `ModelResidencyRecordV1`,
reserved `InferenceTurnLeaseV1`, context receipt и sampling/config. `deferred`
создаёт bounded durable queue/waiting Execution без inference receipt; каждый будущий
model turn получает собственный fresh receipt. Capability/Kernel/store readiness и
model readiness никогда не сворачиваются в один обязательный boolean/lease.

Создать runnable Execution можно только с действующим Execution receipt; model turn
дополнительно требует inference receipt. Если immediate model reservation невозможна,
Product Facade либо создаёт явно durable `queued` Execution
с bounded waiting/terminal timeout и без обещания запуска, либо завершает Interaction
typed blocked outcome. Между receipt и first activation Scheduler повторно проверяет
binding; expiry/revision mismatch не dispatch-ит effect, а переводит Execution в
recoverable waiting/blocked. Так runtime loss становится persisted transition, а не
TOCTOU между UI-проверкой и реальным запуском.

### 13.2. После receipt

Если модель стала недоступна после Kernel receipt:

- receipt и evidence сохраняются;
- effect не объявляется failed и не повторяется;
- Execution получает `partial` или `waiting-for-runtime` по recoverability;
- deterministic workflow/certifier может продолжить без модели;
- resume использует новый activation generation и existing evidence.

### 13.3. Lease и reconciliation

Каждый activation имеет generation, owner, heartbeat, start-by, deadline и expiry.
После crash Recovery Supervisor:

1. читает journal;
2. классифицирует pending invocation;
3. reconcile-ит idempotent/exactly-identifiable effect;
4. не повторяет indeterminate non-idempotent effect;
5. возобновляет только с новым fenced lease;
6. терминализирует abandoned/zombie interactions.

### 13.4. Progress

Progress fingerprint включает Goal revision, Task Graph state, workflow state,
evidence frontier, inspected schemas и policy revision. Повторный model decision без
изменения fingerprint ограниченно repair-ится, затем блокируется; бесконечный loop
невозможен.

### 13.5. Исполняемый architecture contract P10/A19/A33–A34

`ActivationLeaseV1` — не переименованный V2 runner claim. Он связывает execution,
`schedulerGeneration`, `activationGeneration`, owner, readiness digest, durable
`cancellationGeneration`, heartbeat/start-by/deadline/expiry и CAS revision. На один Execution
допустима ровно одна live activation; takeover возможен только после expiry и только одним CAS
winner. Старый owner не может heartbeat или dispatch после смены generation.

Каждый effect имеет `InvocationAttemptV1`: durable reservation непосредственно перед driver
call, activation/cancellation generations, idempotency class и отдельный outcome receipt.
`AcceptedCancelV1` атомарно увеличивает cancellation generation и немедленно запрещает любой
следующий dispatch. `EngineCancelReceiptV1` подтверждает, до какого Host/driver/turn и с какой
granularity дошла отмена. Если effect уже dispatched, отсутствие ack/outcome никогда не
проецируется как `cancelled`: создаётся `RecoveryCaseV1`, а non-idempotent invocation не
повторяется вслепую. Поздний exact receipt добавляет `LateCorrectionV1`, не переписывая историю.

Resume после Host crash создаёт новую activation и новый `ExecutionReadinessReceiptV1`; при
`modelRequirement=immediate` также новые inference admission/turn lease. Context всегда полностью
rehydrated и подтверждён новым `DriverContextReceiptV1`; старые Host/model/turn/context generations
отклоняются. Для model-free recipe inference lease, наоборот, запрещён. Уже подтверждённый effect

## 14. Evidence, certification и truthful presentation

Certifier проверяет Requirement по capability-owned selector и evidence strength.
Он не доверяет model-supplied binding без runtime validation.

Возможные outcomes:

- `verified` — все required claims/effects доказаны;
- `partial` — часть требований доказана и явно перечислена;
- `blocked` — известная отсутствующая capability/approval/runtime/input;
- `failed` — попытка завершена известным failure;
- `indeterminate` — внешний эффект мог произойти, безопасный replay запрещён;
- `cancelled` — новые dispatch запрещены, уже доказанные факты сохранены.

Outcome Projector строит user message из certificate/partial assessment. Для каждого
failed code есть короткий русский класс и inspectable technical details. `verified`
не появляется из model summary или общего `observationVerified=true`.

### 14.1. Простой пользовательский язык, сложная кухня внутри

Обычный интерфейс показывает только то, что помогает человеку продолжить работу:

- что нужно сделать сейчас;
- что делает Оскар понятными словами;
- требуется ли подтверждение или дополнительная информация;
- получен ли проверенный результат;
- сколько времени заняла работа.

Названия runtime/profile/ABI, токены, SHA-256, внутренние IDs, leases, receipts,
provider protocol, model residency и сырые error codes не являются основным UX и
не показываются без явного диагностического действия. Это не означает удаление
диагностики: полный технический trace остаётся доступен в отдельном developer/support
представлении и не подменяет понятное сообщение пользователю.

Текст должен объяснять конкретное следующее действие, а не устройство Monarch.
Например, вместо сообщения о недоступном provider/runtime показывается «Не удалось
подключиться к MAX. Проверь подключение или продолжи локально»; техническая причина
доступна отдельно. Название `MAX` и краткая отметка «облачная обработка» допустимы,
потому что влияют на выбор и приватность пользователя.

## 15. Steering, children и jobs

### 15.1. Steering

Новый user message сначала persist-ится, затем либо изменяет Goal revision на safe
boundary, либо создаёт новый Interaction. Buffered decision со старым context digest
не может dispatch-ить effect.

Accepted follow-up получает immutable sequence/idempotency receipt и exact relation к
Goal/context revision. До нового decision Scheduler применяет follow-up к Task Graph,
инвалидирует старые decision/context/resource bindings и persist-ит новое safe
boundary. Crash между accept/delivery/apply восстанавливается из inbox/outbox без
потери сообщения или двойного model turn.

### 15.2. Cancel

Cancel — durable command, а не UI flag. После accepted cancel новые Invocation и
effect dispatch запрещены сразу по cancellation generation. Driver возвращает typed
`EngineCancelReceiptV1` с фактической granularity/status; отсутствие ack переводит
Execution в `cancellation-pending`/recovery, но не разрешает новый dispatch. Уже
dispatched non-idempotent effect остаётся receipt/reconciliation problem и не
переименовывается в безопасно отменённый.

### 15.3. Resume

Resume всегда получает новую activation generation и `ExecutionReadinessReceiptV1`.
Только если следующий node требует модель, он получает новый
`InferenceTurnAdmissionReceiptV1` + `InferenceTurnLeaseV1`. Resume token от другого
driver/model/build generation не
принимается. Host crash/cache loss требует full `DriverContextSessionV1`
rehydration/ack. Journal/receipt/evidence остаются authoritative; model proposal не
может повторить уже dispatched effect.

### 15.4. Children

Child Execution получает intersection authority, отдельный budget, Goal subset,
mailbox и terminal report. Он не наследует approval, Safe access или provider grant.
Parent reduce принимает только structured child outcomes/evidence refs.

### 15.5. Jobs

Job хранит schedule, timezone/DST policy, missed-fire policy, goal template, authority
snapshot policy и run history. Каждый fire создаёт новую Execution с актуальной
policy evaluation; schedule сам не является бессрочным approval.

### 17.2. EvaluationManifest и RunManifest

`EvaluationManifestV1` до запуска фиксирует corpus/holdout provenance, contamination
audit, supported languages, capability/risk strata, exact fixtures/oracles,
denominators, stochastic repeats, baseline eligibility и pass rules.
`EvaluationRunManifestV1` после запуска неизменно связывает manifest digest,
repository/build/package, Product Facade route, model/backend/tokenizer/config hashes,
hardware/OS, seeds/sampling, cold/warm label, timestamps и raw result artifacts.

Минимум для product gate:

- не менее 50 independent full tasks на каждый mandatory capability pack;
- внутри каждого pack не менее 25 RU и 25 EN tasks;
- не менее 30 effect tasks на каждый enabled risk class;
- каждое непустое пересечение `pack × language × risk-class` имеет не менее 20
  **distinct fixture clusters**; marginal minima не заменяют intersection minimum;
- stochastic model-driven fixture выполняется по 3 frozen seeds; deterministic path
  — один раз и обязан быть byte/decision stable;
- cold и warm samples публикуются раздельно, минимум 20 каждого на hardware tier;
- 95% Wilson lower confidence bound публикуется рядом с point estimate; point gates
  95% overall/90% class остаются, а нижняя граница не может быть ниже 93% overall и
  85% class;
- zero-tolerance gates считаются по всем повторам и не усредняются.

Statistical estimand — доля успешных **независимых fixture clusters**, не seed-runs.
Одна fixture принадлежит exact pack/language/risk stratum и считается PASS только
если все три frozen stochastic seed-runs удовлетворили required claims, terminal
truth и effect policy; любой unsafe/wrong-effect run делает cluster FAIL. Seed-runs
никогда не увеличивают Wilson `n`; Wilson interval считается по binary cluster
outcomes overall и отдельно для каждого mandatory intersection. Latency/tokens могут
публиковаться по runs, но quality denominator остаётся числом distinct fixtures.
Повторение одного target/template с косметической перефразировкой не создаёт
независимую fixture без provenance/independence review.

Holdout, который использовался для prompt/schema tuning, теряет untouched status.
Baseline допускается к regression comparison только если имеет такой же manifest,
ordinary public route, external request semantics, hardware class и сам прошёл
zero-tolerance safety gates. Для устранения Phase 0F→Product Facade цикла route
identity здесь означает стабильный surface contract `POST /api/oscar/turns`, а не
равенство внутреннего owner: V2 baseline проходит через
`OscarTurnCoordinator.submit`, Astra candidate обязан пройти через
`ProductFacade.submit`. Подмена candidate обратно на V2 owner запрещена; различие
внутренних owners явно записывается в `EvaluationRunManifestV1`.

### 17.3. Non-negotiable quality gates

- false `verified`: 0;
- wrong effect/target: 0;
- permission/Safe/egress bypass: 0;
- zombie running after recovery horizon: 0;
- duplicate non-idempotent dispatch in crash corpus: 0;
- required-capability disappearance: 0;
- ordinary greetings creating Execution: 0;
- real-model full-task success: at least 95% overall and no capability class below
  90% on untouched holdout;
- adaptive/optimized path regression: no more than 1 percentage point against
  approved quality baseline;
- every failed task has typed reason and preserves completed evidence;
- performance SLO passes on the declared minimum hardware, not developer machine
  alone.

### 17.4. Efficiency gates

Baseline and candidate must publish per scenario:

- modelCalls/task;
- input/output tokens/task;
- decision repair rate;
- deterministic/workflow/model strategy share;
- queue/load/generation latency;
- time to first useful action;
- wall time to certified outcome;
- context bytes/tokens and compaction count;
- tool calls, retries and duplicate suppression;
- peak RAM/VRAM and model swaps.

Schema/test green без этих full-task метрик не закрывает агентскую готовность.

## 18. Release boundary Monarch `0.3.0`

Monarch `0.3.0` может включить internal schema substrate раньше, но публично называть
его Astra V3 Agent Runtime можно только если:

1. `astra-core-experience.v1` composition полностью доступна.
2. Пять mandatory capability packs, включая `computer-use-reliability`, проходят
   ordinary-route и installed acceptance.
3. Все `mandatory` problems/scenarios из machine-readable release matrix имеют
   executable acceptance evidence; `optional-disabled`/`deferred` явно не называются
   решёнными и advertise unavailable.
4. Real-model full-task holdout и fault matrix green.
5. Package/install/upgrade/rollback acceptance green.
6. UI показывает только runtime-sourced truth.
7. Disabled advanced profiles честно advertise unavailable.

Единственный release-scope owner —
`config/agent-architecture/astra-v3-release-profile-matrix.v1.json`. Для первого
`astra-core-experience.v1` P17/P18 и A26/A27 разрешены как `optional-disabled`, но
их нельзя включать в заявление «P01–P21 solved». P16/compaction и P21/Computer Use
являются mandatory:
иначе P11 long-context не закрыт. `network-download` может быть disabled, однако A18
остаётся mandatory negative/substitution test: отсутствие pack должно дать typed
unavailable, а не search/false verified.

Открытый reference donor и его запреты зафиксированы в
`MONARCH_ASTRA_V3_OPEN_SOURCE_REFERENCE.md`. OpenHands остаётся primary vertical
reference; Microsoft Agent Framework 1.16.0 выбран вторым donor для workflow,
checkpoint/recovery, typed HITL и child lifecycle invariants; Mastra остаётся
TypeScript comparison lab. Ни OpenHands, ни MAF, ни Mastra/ACP не получают authority,
completion truth или runtime ownership без отдельного adapter/import ADR и product
evidence.

Reference-симуляция `simulate-astra-v3-agent-core-faults.mjs` обязана проверять
стратегию без лишнего model planning, permissive-syntax/strict-semantics gateway,
crash/restart вокруг dispatch/receipt и evidence-bound completion. Это только
архитектурный oracle: он не доказывает реализацию Product Facade, installed runtime,
реальных tool effects или real-model acceptance.

Если к release freeze готов только `agent-core-read.v1`, это engineering preview,
не новый агентский runtime и не основание для заявления, что проблемы V2 решены.
